01 · The shift

Imperative UI → Declarative UI

Imperative

Create view
→
Mutate view
→
Keep in sync

“Find the label, change the text, hide the button, invalidate the table.”

Declarative

State
→
UI description
→
Rendered UI

“For this state, this is the UI.” The framework reconciles the result.

The payoff is simpler synchronization: state is the source of truth, not a pile of mutable view objects.

08 · Proposal thinking

Why SwiftUI layout feels different

Parent
proposes
→
Child
chooses size
→
Parent
places
The layout system is relationship-driven: proposal → size → placement. That’s why “just set a coordinate” is rarely the best first move.

For custom containers, SwiftUI exposes the Layout protocol with sizeThatFits and placeSubviews.

This is the conceptual bridge to custom Layout. Keep the exact algorithm out of the beginner path.
Layout
09 · Layout execution

How SwiftUI actually lays a view out

1 · Parent
proposes
→
2 · Child
chooses size
→
3 · Parent
places child

Proposal

The parent offers a size constraint. It can be fixed, flexible, or partially unspecified.

Measurement

The child chooses the size it wants within that proposal, using intrinsic content and its own layout rules.

Placement

The parent positions the child in its coordinate space, using alignment and the final measured size.

The key question when debugging layout is: what proposal reached this view, and what size did it return?
This is the core execution model. Do not describe SwiftUI as a CSS-like coordinate system. A parent proposes; a child measures; the parent places.

10 · Custom Layout

What the Layout protocol gives you

struct FlowLayout: Layout {

    func sizeThatFits(
        proposal: ProposedViewSize,
        subviews: Subviews,
        cache: inout Cache
    ) -> CGSize {
        // measure subviews,
        // wrap into rows,
        // return container size
    }

    func placeSubviews(
        in bounds: CGRect,
        proposal: ProposedViewSize,
        subviews: Subviews,
        cache: inout Cache
    ) {
        // calculate positions
        // call subview.place(...)
    }
}

Two responsibilities

sizeThatFits
Measure the container given the parent's proposal.

placeSubviews
Put each child at a calculated position.

Optional cache

Use Cache to retain expensive measurements between layout passes when useful.

Typical custom layouts: flow/wrap layouts, tagged chips, dashboards, radial arrangements, specialized responsive composition.

The Layout protocol is the escape hatch for custom geometry. Keep the implementation deterministic and separate measuring from placement.

22 · @Binding

A binding is a read/write connection

struct Parent: View {
    @State private var enabled = true

    var body: some View {
        Child(enabled: $enabled)
    }
}

struct Child: View {
    @Binding var enabled: Bool

    var body: some View {
        Toggle("Notifications",
               isOn: $enabled)
    }
}

Flow

Parent state
↔
Binding
↔
Child control

The child can edit the parent's source of truth without owning a duplicate.

Binding solves the “child needs to edit parent state” problem. It is about connection, not ownership.

23 · Single source of truth

Store the minimum; derive the rest

Avoid duplicated state

var items: [Item]
var itemCount: Int
var hasItems: Bool

Prefer derived values

var items: [Item]

var itemCount: Int {
    items.count
}

var hasItems: Bool {
    !items.isEmpty
}
Every extra mutable copy creates another synchronization problem.
This principle is shared by modern declarative systems, including React and Compose: keep the canonical state and derive views from it.

25 · ObservableObject

ObservableObject: the legacy observation contract

final class ProfileModel: ObservableObject {
    @Published var name = ""
    @Published var isLoading = false
}

What it means

ObservableObject makes the model's changes observable to clients that subscribe to the object's change stream.

It belongs to the Combine-era SwiftUI model and remains important when maintaining existing applications.

Introduce the name first. Then explain that @Published is a property-level publisher mechanism layered on top.

26 · @Published

What does @Published actually mean?

@Published var name = ""

Mechanics

Property changes
→
Publisher emits
→
Object observers react

It is a Combine property wrapper. It publishes a change stream associated with the property; it is not simply a generic SwiftUI “state keyword.”

This is why ObservableObject + @Published is conceptually different from modern @Observable + Observation.
Emphasize that @Published is about publishing values into Combine. The modern Observation system uses a different mechanism for dependency tracking.

27 · StateObject vs ObservedObject

Old model: lifetime vs reference

@StateObject

The view creates and owns the observable object.

@StateObject
private var model = ProfileModel()

@ObservedObject

The object is supplied from elsewhere; this view observes it.

@ObservedObject
var model: ProfileModel
The question is not “which wrapper is newer?” It is “who owns the object's lifetime?”
This distinction matters when reading and maintaining older SwiftUI architecture.

28 · Modern Observation

@Observable: make the model observable

import Observation

@Observable
final class ProfileModel {
    var name = ""
    var isLoading = false
}

What changed?

The model declares observability at the type level. You do not manually add @Published to every observed property.

@Observable Observable fine-grained tracking
Apple introduced Observation to simplify model-data flow and make dependency tracking more targeted.

29 · What observation tracks

Dependency tracking follows what the view reads

struct ProfileHeader: View {
    let model: ProfileModel

    var body: some View {
        Text(model.name)
    }
}
ProfileHeader
reads
model.name
→
dependent view updates

Observation can track property access rather than treating every property of a model as equally relevant.

Be precise: this is about dependency tracking and invalidation, not a promise that only one text node will ever be reevaluated.

30 · Owning an @Observable model

Modern ownership: @State can own the observable instance

@Observable
final class CounterModel {
    var count = 0

    func increment() {
        count += 1
    }
}

struct CounterView: View {
    @State private var model = CounterModel()

    var body: some View {
        Button("\(model.count)") {
            model.increment()
        }
    }
}

Read this as

@State
owns
model

The model's lifetime follows the view's state storage, while Observation tracks the model's used properties.

The important mental shift: “state wrapper” and “observable model” solve different problems and can be combined.

29 · @Bindable

When controls need bindings into an observable model

@Observable
final class Book {
    var title = "Sample Book"
    var isAvailable = true
}

struct BookEditView: View {
    @Bindable var book: Book

    var body: some View {
        Form {
            TextField("Title", text: $book.title)
            Toggle("Available",
                   isOn: $book.isAvailable)
        }
    }
}
@Bindable bridges an Observable model to the binding-based controls SwiftUI already knows how to use.
This is one of the most useful modern Observation patterns to memorize.
